# RC003 Windows 实机排查记录

测试环境：Windows 11，蓝牙直连小米语音遥控器，设备标识 VID 2717 / PID 32B8，VB-CABLE。

## 已复现并修正的问题

- 蓝牙接口使用 `Dev_VID&012717` 路径，旧白名单未包含该格式。
- BLE 设备是 AssociationEndpoint，须用对应种类及 `System.Devices.Aep.ContainerId` 查询；HID 接口则经设备实例查询设备节点的 Container ID。两个通道现在能匹配同一实体设备，并排除另一只同厂商键盘。
- 向导将第四步之前的按键当成测试通过。现在只接受第四步内的新按键，重新进入会重置结果。
- 遥控器 OK 同时是 Enter，会触发焦点所在的“下一步”。第四步现在处理窗口内的导航键，Raw Input 仍单独接收按键事件。
- 本机遥控器直接发送 ATVV `AudioStart`，没有先发 `StartSearch`。旧实现会在 Idle 状态立即关麦。现在接受就绪连接的新会话，同时保留取消、结束会话及重复旧会话保护。
- `hDevice=0` 的注入事件被测试环境特例放行，形成 SendInput 反馈循环。现已拒绝没有实体来源的输入。

## 按键覆盖

| 按键 | 本机事件与状态 |
| --- | --- |
| 上、下、左、右、OK | Raw Keyboard 按下、松开均收到；方向键及 OK 已实机验证，OK 不再跳页 |
| Home、Menu | Raw Keyboard 事件已收到 |
| TV | 收到 VKey C0 / MakeCode 29；LiveTv 映射已实机验证 |
| 电源 | 收到 VKey FF / MakeCode 5E；Power 映射已实机验证，其他 FF 不应判为 Power |
| 语音 | ATVV AudioStart/AudioStop；已实机验证第五步电平响应及松开结束 |
| Back、音量加、音量减 | 本机逐键重复操作时未收到 Raw Input；当前尚未支持 |

Back/音量排查：HID GATT 服务 1812 的特征枚举返回 AccessDenied。另行订阅可访问厂商服务 8a7a0001 下三个 Notify 特征，持续监听期间逐键按压仍无通知；同轮“上”键能正常到达 Raw Input。该结果只描述本机与本次固件，不代表所有遥控器或 Windows 版本。

## 验证边界

自动测试覆盖连接就绪状态恢复、过期连接标志拒绝、第四步新按键要求、记录到的 Windows 键码及注入事件拒绝。本机微信输入法 Ctrl+F5 的真实转写已验证（见下文）；其他输入法、主界面映射与所有恢复场景仍须单独实机验收，不能用音量条跳动代替转写成功。

诊断只保存在本地；不记录语音音频或转写文本。

## 微信输入法联动排查与优化

- 微信输入法可配置语音快捷键；本项目微信预设采用实机验证过的 `Ctrl+F5`。快捷键解析器也支持仅含修饰键的组合。
- 在 `NativeInputSender` 中为 Win 键（`VK_LWIN`、`VK_RWIN`）及方向键等扩展键补齐了 `KEYEVENTF_EXTENDEDKEY` 标志，确保全局钩子与输入法热键层能够准确识别 Win 键组合。
- 优化了遥控器固定 `sessionId = 0` 导致二次按键被拒的缺陷：通过 500ms 窗口防抖并在 `AudioStop`/断连/新会话启动时清除 `_lastEndedSessionId`，避免了遥控器在首轮会话结束后永久无法开麦的问题。
- 优化了向导第四步按键过滤：保留方向键与回车（OK 键）防跳页拦截的同时，解除了对物理键盘 `Escape` 的屏蔽，恢复了常规窗口退出交互。
- 含 F5 的快捷键不执行原有 F5 清理抬起；在 Hold-to-Talk 注入按住期间，由程序持有 F5，拦截额外的物理 F5 Down/Up，放行注入事件。结束或断连后恢复普通 F5，避免硬件连发重复触发输入法或提前抬起程序持有的键。
- 微信输入法与本机应用配置均设为 `Ctrl+F5`；应用预设和微信输入法自身的快捷键必须一致。

### 2026-11-02 后续联动排查

- 实体键盘左 Ctrl + 左 Win 可激活微信输入法；遥控器触发的同组合键虽被 SendInput 接受，仍未出现微信语音面板。补齐 Win 扩展标志、按键间隔实验和会话开始补发 F5 Up 均未单独解决，不能据此宣称已修复。
- 按用户选择，F5 钩子现在在 Opening/Streaming 期间直接拦截物理 F5 Down，不再要求 Raw Input 先完成 Arm；保留注入清理事件与物理抬起事件，禁用防护时仍旁路。空闲且未被已验证的遥控器事件 Arm 时，不拦截普通键盘 F5。
- 该范围不保证拦住早于 Opening 的首个 HID F5；未采用“遥控器连接期间全局屏蔽 F5”的方案。微信是否受首键或注入兼容性影响仍待实机验证。
- 向导第六步拒绝空或无法解析的快捷键，并保留上一次有效配置，避免带空快捷键进入转写验收。

### Ctrl+F5 持续转写验收

- 切换到 Ctrl+F5 后可以唤起微信，但完全旁路 F5 防护时，微信在遥控器仍按住时提前结束。受控长按测试中，蓝牙流仍持续到松开，AudioStop 原因为 0x02，排除了该次蓝牙提前停流。
- 加入程序持有 F5 期间的物理事件拦截后，2026-11-02 15:18:43–15:19:09（本机时间）会话持续约 25 秒，统计拦截 759 次物理 F5 Down 和 1 次物理 F5 Up。用户确认微信持续识别到松开且文字成功上屏。
- 保活提前到每秒一次的实验未解决微信提前停止，已恢复 8 秒周期；保留写入状态记录、会话代次检查和防止重叠写入。AudioStop 记录实际原因码，不再把所有停止都解释为松开。
- 88 项自动测试通过（测试集合串行运行，避免现有静态 AppLogger 测试相互争用）；覆盖持有期间物理按下/抬起拦截、注入事件放行、Clear 后恢复及非 F5 快捷键不启用持有拦截。

### 2026-11-02 最新版回归排查

- 最新版语音结束后普通键盘异常；`GetAsyncKeyState` 包含程序注入状态，不能用它判断 Ctrl 是否由实体键盘按住。持有快捷键的松开路径现成对释放注入的所有按键，并移除已成功释放的跟踪记录；保持活动语音期间的 F5 连发拦截不因 5 秒超时失效。实机用户确认修复后普通键盘正常。
- 同机、同样的 Ctrl+F5 设置下，新版在微信面板保持打开时只上屏前几个字；仅移除显式 `MediaFoundationResampler`、保留增益和滤波后，用户反馈长句识别基本完整、明显改善。约 18 秒会话持续到松开，拦截 554 次物理 F5 Down。检测和播放现使用相同的 16 kHz 单声道输入路径；其他音频设备和格式仍需验证。
- 131 项自动测试串行通过，覆盖 Ctrl+F5 的成对释放及超过 5 秒时的 F5 保护。默认并行测试仍可能因共享 AppLogger 的日志文件争用而失败。
